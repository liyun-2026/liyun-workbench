## 二、今晚的实测数据（真实跑出来的）

测试方式：本机直连（绕过代理）反复请求线上站点。

### 打开页面

| 阶段 | 耗时 | 说明 |
|---|---|---|
| DNS 解析 | 25 ms | 很快，不是瓶颈 |
| TCP 连接 | 251 ms | ← **跨境 RTT 开始显现** |
| TLS 握手 | 499 ms | ← 再加一次往返 |
| 首字节 TTFB | **861 ms**（中位 943 ms） | ← **这部分压缩、减体积都救不了** |
| 纯下载 88 KB | 249 ms | ← 可优化 |
| **打开总计** | **约 1.2 秒** | |

### 关键点：我原本的判断是错的

我一开始看到页面 265 KB、下载速度只有 200 KB/s，以为「下载占了一半，所以要拼命砍体积」。
**这个判断被实测推翻了：**

- EdgeOne **已经自动开了 Brotli**，265 KB 压到 **87.6 KB（-67%）**——这条路平台已经替我们走完了；
- 但压缩后总耗时**反而从 1.7s 涨到 3.0s**（单次样本），说明拥堵的不是体积；
- 反复 5 次中位后真相清楚：**TTFB 943 ms（握手+跨境往返）占了大头，下载只占 249 ms。**

> **修正后的结论：瓶颈是跨境物理延迟，不是页面大小。**
> 所以「把学生端做成 60 KB」这件事收益有限，**不值得为此重新设计架构**。真正有效的是下面第五节那五招。

### API 请求

| 场景 | 耗时 |
|---|---|
| 全新握手一次 API | 平均 **1356 ms**（最慢抖动到 2320 ms） |
| 其中握手占 | 666 ms |
| **同一条连接复用** | **0.81s → 0.25s → 0.27s** ✅ 省掉整个握手 |

**这条最有价值**：复用连接能让单次操作从 ~1.4 秒降到 ~0.25 秒，整整 **5 倍**。

## 四、这直接决定了设计取向

既然瓶颈是「每次新连接要 0.5~0.9 秒握手」，那么设计原则就一条：

> **能不发请求就不发，能晚发就晚发，能让用户先看到东西就先看到东西。**

具体到学生端，就是**离线优先（Offline First）**：

- 学生打开 → 立刻用本地数据画出完整界面（**完全不走网络**，耗时几乎为 0）
- 后台悄悄补拉最新数据 → 到货后无感替换
- 打卡 → **点了立刻显示成功**，写入本地队列，后台慢慢传

这样即使跨境链路一次要花 1.4 秒，**学生手指点下去那一刻也感觉不到等待。**

## 五、不备案情况下的五招优化（按性价比排序）

### 第 1 招：Service Worker 预缓存 App Shell ★★★★★
- **做什么**：HTML/CSS/JS/图标安装时存进浏览器
- **收益**：第二次起不再下载 App Shell，**下载 249 ms 直接归零**
- **成本**：几乎为零，一个 sw.js 即可

### 第 2 招：本地数据快照，首帧先渲染 ★★★★★
- **做什么**：上次拉到的数据存本地，打开先画旧数据
- **收益**：用户「看到内容」的时间从 **1.2 s → 约 0.05 s**（肉眼无感）
- **代价**：开头半秒显示的是上次的数据（一般不会有人察觉，随后被新数据覆盖）

### 第 3 招：首屏数据合并成 1 个请求 ★★★★☆
- **做什么**：新增一个 `boot` 接口，一次返回打开首屏所需的全部数据
- **收益**：原本 5~6 个串行请求 ≈ 3.4 s → **1 个请求 ≈ 0.25 s**
- **依据**：这是今晚最贵的部分——握手一次就要 666 ms，多个请求就是多次握手

### 第 4 招：连接保活 + HTTP/2 复用 ★★★★☆
- **做什么**：JWT 令牌有效期内保持长连接，所有请求走同一条链路
- **收益**：实测 **1.4 s → 0.25 s**
- **成本**：零，浏览器/平台本就支持

### 第 5 招：打卡本地乐观处理（必做）★★★★★
- **做什么**：学生点「打卡」→ 本地立刻记录 + 显示「已打卡」→ 后台补传
- **收益**：**用户感知 0 秒**，哪怕网络要 3 秒也不影响打卡成败
- **理由**：打卡是全场唯一有时间敏感性的操作（课前 3 分钟 80 人集中点），也是最堵的时刻。**必须让它脱离网络才能用。**

### （第 6 招：平台已自带 Brotli，不用管）
265 KB → 87.6 KB，已经自动生效。**学生端不必为体积再较劲。**

## 六、80 个人一起用，撑得住吗？

### 请求量
- 边缘函数免费额度：**300 万次/月**（官方文档）
- 静态加速请求：**不限量**
- 80 人 × 每天 10 次 API × 30 天 = **2.4 万次/月** → 用到 **0.8%**

### 打卡峰值
- 课前 5 分钟内 80 人打卡 = **0.27 QPS**
- 这条链路完全无压力（我今晚连测几十次都没出现过失败）

### 存储空间
- 一天打卡记录约 80 条 × 200 字节 ≈ 16 KB/天 → **约 5.8 MB/年**
- KV 容量 1 GB → 用不到 **1%**

### 地图/定位/短信费用
- **全部 ¥0。** 不接地图 SDK（自己写 Haversine 距离计算）、不发短信

> **结论：80 人规模下，免费额度用到不到 1%。这条路走得通。**
