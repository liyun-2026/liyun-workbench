# 砺蕴工作系统 · 学生端综合方案（v2 · 问题与对策）

> 版本：v2（综合稿）　日期：2026-09-23　适用规模：在校学生约 80 人
> v1（`docs/学生端建设方案.md`）回答的是"做哪些板块"；这一版回答的是"**会出什么问题、怎么解**"，两版一起看。
> 一句话结论：**学生端的数据以服务端为准，本地只做缓存**——这条原则定了，打卡作弊、存储被清、换手机这三件最容易出事的事就都有解了。
> 成本结论不变：**不新增任何付费服务，¥0 可开工**。

图例：**P1** 一期必做　**P2** 二期　**—** 明确不做

| 9 | **我的档案** | 只我自己：考勤、作业、模考三科强弱、老师评语、晚自习记录 | 任何他人数据 | **P2** |

| 13 | 家长端 | — | 等学生端跑顺半年再说 | **—** |

**为什么首屏必须是"今日"**：学生打开系统只为两件事——今天上什么课、现在该不该打卡。没有这个聚合页，打卡按钮会被埋在二级页面里，学生每天要多点两下，久了就不用了。

**学生端总入口**：同一个网址 `https://liyun2026.top`，登录后按账号角色自动进学生端，不需要第二个地址，也不需要学生选身份。给学生发的是一条链接 + 用户名 + 初始密码。

## 二、打卡：会出什么问题，怎么解

打卡是学生端**唯一有时间敏感性**的操作，也是唯一会被"想办法绕过去"的操作。逐个说。

### 问题 1　改手机时间就能假装没迟到

- 前端 `Date.now()` 完全不可信：系统设置里改一下时间，迟到就消失了。
- **解法**：判定一律用**服务端时间**。打卡走后端 `action:'sign'`，迟到与否由服务端 `Date.now()` 与作息表比对得出，客户端只负责显示结果。
- **延伸**：`pull` 响应里带回 `serverNow`，前端算出本地时钟偏差 `offset`，显示倒计时、课程时间都用校正后的时间——学生看到的钟和教务办公室的钟是同一个。

### 问题 2　人在宿舍，让同学帮忙打

- **不做人脸识别**（成本、隐私、实操三头都不划算）。用三层递进，从"宽松"到"严格"由您选：

| 强度 | 做法 | 优点 | 代价 |
|---|---|---|---|
| ① 宽松 | 只记设备指纹 + 时间 + 距离，教务端自动标黄异常 | 零成本、不打扰 | 需要老师人工核对 |
| ② 中（**推荐**） | **老师端动态码**：老师或教务的屏幕上每 60 秒换一个 6 位码（或二维码），学生扫码/输码，码由服务端密钥生成，学生端拿不到密钥 | 几乎杜绝远程代打；不用新增硬件；老师本来就在教室 | 需要老师在现场 |
| ③ 严格 | 定位围栏（距校区 ≤150 米） | 自动、不需老师介入 | 室内 GPS 漂移 20~100 米，微信内置浏览器常取不到，会误判 |

- **我的建议：② 为主，③ 为辅，① 兜底。** 有老师在教室就用动态码；老师不在（早功、晚自习）退回定位围栏 + 异常留痕；两样都失败时允许"待核"打卡，由教务第二天核对。
- **异常自动标黄**（教务端「今日打卡」一览）：同一台设备出现多个学生、距离明显异常、上课前 10 秒内集中打卡。标黄不是惩罚，是提醒班主任看一眼。

### 问题 3　没网 / 弱网，打不上卡

- 学生端和教务端在这里**原则相反**：教务端是"本地优先、离线也能记账"，学生端**必须服务端确认**才算打卡成功，否则等于没有凭证。
- **解法**：断网时打卡写入本地"待补传"队列，界面显示**"已记录，联网后自动提交"**，状态为"待核"。联网后自动补传。
- ⚠️ 关键一条：补传的打卡**一律按服务端收到时的时间判定迟到**，不按学生断网时的本地时间。这样"故意断网逃避迟到"这条路是堵死的——断网只会让结果更不利，不会更划算。
- 界面上要写清楚这句话，学生自然就不会动这个念头。

### 问题 4　重复打卡、误打卡

- 一天一人**一条记录**（`sign:{日期}`，id 即学生 id），重复提交是覆盖，不会堆成一片。
- 覆盖以**最后一次**为准（可能是定位失败重打、老师让重打），但每次尝试都留 `attempts`（最多 5 条：时间、方式、设备、距离），教务端「今日打卡」能展开看。
- 教务端有**补签 / 改判**按钮，写进去的记录标 `by:'manual'`，统计时可与自助打卡分开看（学生忘带手机、手机没电都靠它）。

### 问题 5　室内定位漂、微信里打不了卡

- 半径默认 **150 米**（50 米会大量误判），同时记录定位精度 `acc`，精度差时仍允许打卡，但标记"存疑"。
- 检测到微信内置浏览器时，页面顶部提示"请点右上角 ··· 用 Safari/Chrome 打开"；已经**添加到主屏幕**的学生不受影响，所以入校时统一引导一次加桌面。
- iOS 必须 HTTPS + 用户点"允许"才能定位——我们的站已经是 HTTPS，这一条满足。

### 问题 6　80 人同时打卡会不会挤爆

- 上课前 5 分钟 80 人 ≈ **0.3 QPS**，边缘函数毫无压力，不需要队列。打卡是一人一条独立记录，不做共享大数组，不存在写冲突。

**打卡记录长什么样**

```js
{ id:'s123', studentId:'s123',
  at: 服务端时间戳,                  // 权威，改不了
  way: 'code' | 'geo' | 'manual',    // 动态码 / 定位 / 教务补签
  lat, lng, acc, dist,               // 定位证据（way='code' 时可为空）
  status: '正常' | '迟到' | '待核',
  lateMin: 0,
  dev: 'a9f3…',                      // 设备指纹（UA+屏幕哈希），不是隐私
  by: 'self' | 'manual',
  attempts: [ { at, way, dist } ] }
```

**迟到怎么定**：`服务器时间 > 上课时间 + 宽限（默认 5 分钟）` 即迟到，界面直接显示"迟到 6 分钟"。
打卡产生的"迟到 / 病假 / 事假"直接写进现有 `att:{日期}`，由**已有的"考勤自动进量化"**接管扣分——教务不用记第二遍。

## 三、存储与数据：会出什么问题，怎么解

这是学生端最容易翻车的一块，因为学生的手机环境远比您和老师的复杂：微信里打开、无痕模式、清理内存、换手机。

### 问题 1　在微信里打开，数据存不住

- 微信内置浏览器（iOS 是 WKWebView、安卓是 X5 内核）的 localStorage **随时可能被清**，且不保证跨天保留。
- **解法（根本解法）**：**学生端不依赖本地存储保存业务数据**。所有东西每次打开都从服务端拉，本地只留一份缓存用来"秒开"，缓存没了重新拉即可，不涉及任何丢失。
- 具体：学生端只有两类本地写入——① 打卡的"待补传"队列（最多 7 天，传完即清）；② 界面偏好（看到哪一页、新闻读没读）。其余一律不落本地。
- 页面检测到微信内置浏览器时给一次提示，引导学生用系统浏览器打开并**添加到主屏幕**。

### 问题 2　iOS Safari 七天不访问就清数据

- 这是 Apple 的 ITP 规则，谁都改不了。但**添加到主屏幕的 web app 不受这条限制**。
- **解法**：入校引导里把"添加到主屏幕"做成必做一步（和现有 PWA 一致，已有 `manifest` 与图标）。加到桌面后既是独立图标、存储也更稳、还少了地址栏那一截。

### 问题 3　无痕模式 / 浏览器不让存

- 系统已有降级方案（存不了就退到内存，只是关掉页面就没了）。
- **解法**：学生端检测到存储不可用时，明确提示"请退出无痕模式再打开"，而不是默默让它"看起来能用、其实记不住"。

### 问题 4　换手机、多设备

- 学生端**不绑死设备**（绑死会很麻烦：丢手机、借手机都打不上卡）。账号密码在哪台设备都能登。
- 设备指纹只用于**异常留痕**（同一台设备出现多个学生会被标黄），不影响正常使用。

### 问题 5　学生端会不会把教务的数据冲掉

- 这是**最严重**的一条，也是唯一可能出大事的一条。
- **三层防线**：
  1. 后端新增 `STUDENT_WRITE` 白名单：学生只能写 `sign:{日期}`、本人的 `tickets`、自己的个人区设置，**其余一律拒绝**（服务端拒绝，不是前端隐藏）；
  2. 后端 `STUDENT_READ` 白名单：只下发"本人相关 + 全站公开"的键，名册、量化细则、AI key、账号列表**根本不下发**；
  3. 测试里钉死一条硬指标：**学生账号登录后同步一圈，教务端的数据条数一条都不能少**（现有 `test/permissions.test.mjs` 会加这一节）。

### 问题 6　容量会不会撑爆

- 学生端缓存只有课表、新闻、通知，全是文字，一年也不到 1 MB。
- 规则：新闻缓存只留最近 3 天；打卡待补传队列超过 7 天自动丢弃（那种情况下早已失去时效）。

### 问题 7　数据归谁、怎么备份、毕业了怎么办

- 数据都在您自己的机构共享区（`org/data`），**不在任何第三方手里**。
- 备份走教务端已有的「导出备份」（会把 `sign:`、学生工单一并导出）；建议每周导出一次，存微信文件传输助手。
- 学生毕业 / 退学：教务端**停用账号**（不是删除），数据保留，离开满一年后可清。停用的账号立刻登不进去，但历史记录还在。

### 问题 8　隐私：学生能看到别人的东西吗

- 不能。后端按 `studentId` 过滤后才下发：考勤、作业、成绩、量化明细、体重、老师评语**只含本人**；`notices`、`news_cache`、课表、考试安排是公开的，全体可见。
- 班级量化只给"班级总分 + 本期变化 + 本人明细"，**不出他人姓名、不做排名**——这一点既是隐私，也是少惹矛盾。

## 五、网络与速度

站点走境外节点（免备案路线），实测冷启动约 1.2 秒，其中 **943 毫秒是跨境握手的物理成本**，压体积救不了。

缓解五招（沿用治理教务端时的结论）：

1. **App Shell 缓存**：第二次打开起，页面本体走本地，开屏立刻能动；
2. **本地快照**：课表、新闻这类不变的数据先显示上次的，联网后更新；
3. **连接保活**：同一场会话内复用连接，省掉重复握手；
4. **首屏请求合并**：打开时一次把"今日课程 + 作业 + 通知 + 打卡状态"取齐，不一个一个等；
5. **打卡乐观 UI**：点了立刻显示结果，网络在后台走完——学生不会盯着转圈。

升级触发条件（届时再考虑备案）：多数学生反映转圈、晚高峰明显变慢、人数超过 150。切的是加速区域，**域名和代码都不用动**。

## 七、分期与验收

**一期 · 能用起来（建议先做这个）**
1. 学生角色 + 批量建号；
2. 打卡闭环：教务端「打卡设置」+ 学生打卡 + 迟到判定 + 教务端「今日打卡」一览（含标黄、补签、改判）+ 打卡自动写进考勤；
3. 请假：学生提交 → 教务批准 → 自动写考勤 → 自动进量化；
4. 学生端首屏「今日」+ 每日新闻（只读缓存）+ 我的课表 + 设置。

**二期 · 完整**
5. 考试抽签（教务开抽 / 名单 / 重抽；学生看本人序号）；
6. 本班量化（班级分 + 本人明细）；
7. 我的档案（本人考勤、作业、模考三科强弱、老师评语）；
8. 我的作业（当日作业 + 我的提交状态）；
9. 老师端可看本班学生今日打卡（只读）。

**三期 · 可选**
10. 打卡月报导出；11. 作业拍照提交（届时再评估流量）；12. 家长端。

**验收**（每期都要跑，全绿才推线上）
- 权限测试新增学生角色一节（≥15 项：越权读他人成绩 / 名册 / 量化细则被拦、写白名单、同步后教务数据不减）；
- 真 Chrome 端到端跑通：建号 → 学生打卡 → 教务看到迟到 → 量化自动扣分 → 学生请假 → 教务批准 → 考勤写入；
- 弱网与断网专项：断网打卡能存、联网能补传、补传按服务端时间判定。

## 九、一句话总结

学生端不换架构、不加付费服务：**时间以服务端为准，数据以服务端为准，本地只做缓存**——
这三句话定下来，改时间、换手机、微信里打开、断网打洞这些事就都只是"看一眼标记"，不再是事故。
