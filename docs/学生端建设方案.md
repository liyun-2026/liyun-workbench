> 版本：v1（讨论稿）　日期：2026-09-20　适用规模：在校学生约 80 人
> 定位：**先给结论和取舍，再给做法**。这一版是用来拍板的，不是开发任务书。
> 一句话结论：**不新增任何付费服务就能做**，整套建立在现有「单文件 PWA + EdgeOne Pages + 边缘函数 + Blob 存储」之上；

## 一、目标与硬约束

| 项 | 要求 | 本方案怎么满足 |
|---|---|---|
| 规模 | 80 名学生，可能同一时段集中操作 | 打卡走"每人一条独立记录"，不做共享大数组；峰值约 0.3 QPS，毫无压力 |
| 流畅 | 手机端点开就出、点完就走 | 学生端只渲染 5 张卡；只读经过服务端过滤的小数据集；OCR 等重资源不进学生端 |

| 可维护 | 教务一个人也要管得过来 | 学生账号批量建（80 人 1 分钟）；打卡/请假/抽签全部在教务端有对应的"收口"页面 |
| 隐私 | 学生只能看到自己 | 后端新增学生白名单，按"本人 studentId"过滤，姓名/成绩/考勤一律不外泄 |

## 四、六个关键设计（这是方案的核心，决定能不能落地）

### 4.1 定位打卡：不接地图 SDK，用"采集坐标 + 算距离"

**教务端一次性设置（在「打卡设置」里）**

1. 站在教室/校区里，点「📍 采集当前位置」→ 浏览器返回经纬度，存下来；
2. 设允许半径（**默认 150 米**，室内 GPS 漂移普遍 20~100 米，设 50 米会误判）；
3. 设可打卡时间窗（课前 60 分钟 ~ 课后 30 分钟）；
4. 设今日上课时间与迟到线（见 4.2）。

**学生端打卡流程**

```
点「📍 打卡」
  → 浏览器请求定位权限（HTTPS 下才可用，我们的站已经是 HTTPS）
  → 拿到 {lat, lng, accuracy}
  → 提交给后端 action: 'sign'
  → 后端算：① 与校区坐标的直线距离（Haversine）
            ② 用【服务器时间】判断是否迟到
  → 返回 { status: '正常' | '迟到', lateMin, distance }
  → 学生端显示结果；记录落库
```

**为什么不需要腾讯/高德地图 SDK**：教务采集坐标和学生上报坐标都来自浏览器原生接口，同属 WGS-84 体系，
两点之间算距离只要一条 Haversine 公式（约 15 行代码）。**不需要纠偏、不需要逆地理、不需要加载任何地图 JS**。
好处有三：省一笔调用费、省 200KB+ 的 SDK 加载、境外节点下也不会因为地图资源加载慢而卡住打卡。

**打卡记录结构**（`sign:{日期}`，一人一条，id = 学生 id）

```js
{ id:'s123', studentId:'s123',
  at: 服务端时间戳,          // 权威时间，客户端改不了
  lat, lng, acc: 32,        // 精度（米）
  dist: 87,                 // 与校区的距离
  status: '正常' | '迟到',
  lateMin: 0,
  dev: 'a9f3…',             // 设备指纹（UA+屏幕等哈希），不是隐私信息
  by: 'self' | 'manual',    // 自己打的 / 教务补签
  note: '' }
```

同一天重打 = 覆盖（upsert），以最后一次为准，不会堆重复记录。

### 4.2 "今天上课时间可调" + 迟到线

教务端「打卡设置」存两份：

- **默认规则**（按班）：`{ clsId, startAt:'08:30', lateAfter:5, windowBefore:60, windowAfter:30 }`
- **今日临时覆盖**（按天）：`sign_day:{日期}` —— 集训、周末课、临时调课时，**只改今天**，不动默认。

> 迟到判定 = `服务器时间 > startAt + lateAfter` 分钟。
> 例：8:30 上课、宽限 5 分钟 → 8:35:01 打就是迟到，界面直接显示"**迟到 6 分钟**"。

**时间权威很重要**：学生把手机时间改到 8:00 就能"假装没迟到"。所以：
① 判定一律用**服务器时间**（后端 `Date.now()`）；
② 后端在 `pull` 响应里带回 `serverNow`，前端用它校正本地时钟偏移后再显示倒计时，
这样学生看到的倒计时和教务端的时钟是同一个。

### 4.3 请假：复用现有工单链路，批准后自动进考勤与量化

```
学生提交请假（日期 + 病假/事假 + 原因）
   → 落 tickets（type:'学生请假'，带 studentId、日期、假别）
   → 教务端「协作 → 待办」出现，带「批准 / 驳回」
   → 批准：服务端/教务端把该生该天的考勤写成 病假/事假
   → 现有「考勤自动进量化」机制接管，扣分自动发生
   → 学生端看到「已批准」，当天打卡按钮自动变为「今日已请假」
```

关键点：**请假不是另开一套审批表**，而是现有工单的一个新类型 —— 教务不用学新东西，数据也不会分叉。

### 4.4 考试抽签：用"确定性算法"，不靠服务端随机

80 人同时点"抽签"，如果让服务端一个个随机分配序号，Blob 存储没有事务，**会撞号**（两人抽到同一个号）。
所以换一个思路：

1. 教务端点「开始抽签」→ 生成一个随机 `seed`，存进共享区 `exam_draws`；
2. 学生端打开考试页 → 读到 `seed` → **本地用同一个算法算出自己的序号**；
3. 算法是确定性的：`先把学员 id 排序（保证所有人算的初始序列一致），再用 seed 驱动的伪随机做 Fisher-Yates 洗牌`；
4. 结果：每个人的序号唯一、不重不漏、**所有人都算得出同一份名单**、不需要服务端原子写、零并发冲突；
5. 学生**不能重抽**（seed 只有教务能改）；教务端可「重新抽签」（换 seed，次数 +1，留痕）。

```js
// 前后端共用的同一段代码，任何人算出来都一样
function drawOrder(ids, seed){
  const rng = mulberry32(hash(seed));
  const a = [...ids].sort();                       // 关键：稳定排序
  for (let i = a.length - 1; i > 0; i--){
    const j = Math.floor(rng() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;                                        // 下标+1 即出场序号
}
```

同一套机制可以扩展成三种抽签模式，您选哪个我就做哪个：
- **出场顺序**（默认，最常用）
- **分组/考场**（洗牌后按 N 人一组切块）
- **考题抽签**（题库 id 洗牌后按序号取题，每人一题）

教务端同步看到的：名单 + 序号表 + 已抽签人数 + 「复制名单」「重新抽签」按钮。

### 4.5 每日新闻：学生端只读缓存，不自己拉

现在教务端每天拉一次央视接口并存 `news_cache`。学生端**直接读这份缓存**，
不去请求央视。效果：请求数从"80 人 × N 次"降到"**1 次/天**"，
而且 80 个学生看到的是同一份、同一天的新闻，评述课的素材也统一。
（需确认/小改：把 `news_cache` 从个人区挪到共享区，保证学生拉得到。）

### 4.6 班级量化与作业通知怎么给学生看

- **班级量化**：只给"班级当前总分 + 本期变化"，以及**本人**的加扣分明细
  （如"9/18 迟到 −2"）。**不显示他人姓名、不做排名**，避免隐私与矛盾。
- **作业通知**：本班当天作业 + 我这条是"已交/未交/未登记"，直接读现有数据，不需要教务额外录入。
- 通知（`notices`）在首屏置顶，带"未读红点"。

## 五、权限模型（学生角色怎么防越权）

新增 `student` 角色，账号上挂 `studentId`（一个学生一个号）。

后端新增 `STUDENT_READ` 白名单，**只下发这些**：

| 键 | 学生能看到的范围 |
|---|---|
| `notices` | 全部（公告本来就给大家看） |
| `news_cache` | 全部 |
| `periods / schedule / exams / exam_draws` | 全部（课表、考试安排本就公开） |
| `classes / students` | **只含自己那一条**（用于显示班级名、本人姓名） |
| `homework` | 本班的 |
| `att: / hw: / hwchk: / sign: / exam_scores / weights / records` | **只含本人** |
| `quant_log` | 本班的（但不含姓名，只含班级汇总） |
| `tickets` | **只含本人提交的** |
| 其他所有键 | 一律不下发（名册、量化细则、AI key、账号列表等） |

**写权限更严格**：学生只能写 `sign:{日期}`、`tickets`（本人）、以及自己的个人区设置。
其余一律拒绝。**验收硬指标：学生账号登录后同步一圈，教务端的数据一条都不能少。**

## 七、性能与并发测算（80 人规模）

| 指标 | 估算 | 结论 |
|---|---|---|
| 每日请求数 | 80 人 ×（打开 3 次 + 打卡 1 次 + 同步）≈ **400~800 次/天** ≈ 2.4 万次/月 | 免费版函数额度 300 万次/月，**用不到 1%** |
| 打卡并发峰值 | 上课前 5 分钟内 80 人 ≈ **0.3 QPS** | 边缘函数无压力，不需要队列 |
| 新增数据量 | 打卡 80 条/天 × 约 120B ≈ 10KB/天 → **约 2MB/年** | KV 约 1GB，**占比 0.2%** |
| 学生端首屏 | 实测（不备案） | 冷启动约 **1.2 秒**；App Shell 缓存 + 连接保活后 **0.25 秒**（2026-09-20 实测：跨境握手+等待 943 ms 为不可压缩的硬成本，下载仅 249 ms） |
| 页面体积 | 学生端新增约 700 行（单文件 5500 → 6200 行） | OCR 等重资源仍按需加载，学生端不触发 |

结论：**容量和并发都不是问题，唯一的体验变量是节点位置（见下条风险 R1）。**

## 九、风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
